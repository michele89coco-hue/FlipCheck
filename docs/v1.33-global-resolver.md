## Root cause

The v1.32 architecture separated epistemic levels, but its retrieval parser appended the fields of every Web candidate to the shared evidence ledger before the tournament. A checklist page with several rows therefore became one synthetic identity. The final UI also consumed the legacy candidate list, while V2 only populated a private trace; this produced a zero-candidate diagnostic next to a confirmed title. In parallel, the reducer could fall back to an inferred brand when no grounded candidate survived, image `views` were never imported, and Web retrieval for remotes was text-only and hypothesis-biased.

The result was deterministic contamination:

- numbers from unrelated checklist rows could coexist;
- set, edition and finish from different TCG records could be fused;
- sealed-product format candidates could replace the core family;
- the first inferred electronics brand could anchor every query and the title.

## Candidate isolation

`CandidateRetrieverV2.parse` now creates one `IdentityCandidateV2` per returned record. Parsing does not mutate `ImmutableEvidenceLedgerV2`. Each candidate keeps its source page, isolated record ID, page scope, identity level, matched evidence, contradictions, score, status and disproof outcome.

Only this sequence can write retrieved facts:

1. bind the candidate URL to a URL actually returned by the Web tool;
2. reject generic/multi-record pages that claim to be an exact record;
3. compare the candidate against localized observed atoms;
4. execute profile-specific catalog consistency and disproof;
5. select one winner at the same hierarchical level;
6. commit only that winner to the evidence ledger;
7. execute `FinalStateReducerV2` once.

Rejected or ambiguous candidates remain in diagnostics as `REJECTED`, `AMBIGUOUS`, `LOW_SUPPORT` or `INCOMPATIBLE`; their fields cannot contribute to the public identity.

## Grounding and semantic comparison

- Identity labels reported by Vision are `OBSERVED` only when localized and corroborated by local OCR. Otherwise they remain `INFERRED`.
- A set-name classification derived from a symbol remains inferred; the visible symbol appearance is the observation.
- `SemanticRelationV3` distinguishes `EXACT`, `CANONICAL_EQUIVALENT`, `PARENT`, `CHILD`, `COMPATIBLE_EXTENSION`, `AMBIGUOUS` and `INCOMPATIBLE`.
- Product family extensions such as `Chrome` → `Chrome Basketball` no longer create conflicts.
- Configuration numbers remain strict: “every box” and “every 3 boxes” are incompatible.
- TCG collector denominators are derived as linked normalized atoms; contextual `I/l/1` repair remains corroboration-gated.
- Sports `BASE` is stored as `cardRole`, not as an edition.
- Full seasons and single release years remain distinct but compatible; the title prefers the full observed/catalog season.

## Retrieval and disproof

The v1.33 identity request is multimodal: the original production image data remains attached while the Web tool retrieves catalog records. For electronics and remotes, query zero must exclude every inferred brand/model and use only localized labels and layout. A policy violation rejects that batch and permits one bounded neutral retry only when the cost budget allows it.

`CandidateVerifierV2` recomputes matches from the ledger instead of trusting model-reported counts. Exact card candidates require an isolated source row, number agreement and independent core matches. Remote candidates must return their own structured control layout, shortcut buttons, navigation layout, keypad, voice control and design signature; the app recomputes their layout score against localized photo atoms. A model-reported match list or score cannot supply missing candidate evidence. Disproof is computed before reduction and an inference-only candidate cannot score 100.

## Final state and UI

`FinalStateReducerV2/3` is the sole public state writer. It:

- commits only the selected candidate;
- prevents an inferred-only brand from entering the title;
- propagates uploaded-image views and structured evidence;
- fills the legacy technical candidate table from isolated V2 candidates;
- lists retrieved-but-rejected sources separately from used catalog sources;
- keeps core identity independent from edition, finish, format, SKU, model and market states;
- derives the displayed confidence from observed evidence and the actual winner.

The Android foreground-service path explicitly bypasses the legacy recognition closer for V2 results. `EvidencePolicy` acts only as a read-only V2 evidence presenter after reduction; legacy closure remains available solely for a non-V2 fallback route.

The title uses a readable phrase rather than concatenating unrelated candidate fragments. Sealed subseries are appended only from the same winning record.

## Live release gate

`LiveRegressionSuite` is packaged only in the Android test APK. The five original JPEGs remain test assets and are absent from the release/candidate APK. On an installed v1.33 APK the suite runs each real case three times:

- original fixture through the production image encoder;
- app-recompressed fixture through the same encoder;
- uncached repeat with a new client and file instance.

Every run traverses the real foreground service, ML Kit OCR/barcode, production Vision, production Web search, tournament, disproof, reducer, result store and UI screenshot. It records the exact APK SHA-256, embedded commit, device/emulator, Android version, calls, queries, cost, candidates, views, invariants and final result.

`tools/release/v133_release_gate.py` refuses promotion unless unit tests, replay, live pipeline, installation, launch, all twelve runs, invariants and cost report pass, and the live report SHA-256 equals the supplied APK SHA-256.
